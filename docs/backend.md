# Tenant gateway developer guide and cost estimate

**No-card constraint, 2026-10-19:** do not enable billing or require a payment method. The selected candidate is Firebase Spark plus a Cloudflare Workers Free / SQLite Durable Object HTTP gateway, preserving the existing accounting/authorization core. Local compatibility and native URL-transport verification are being recorded separately; live hosting is not yet approved or deployed. See [the Arabic no-card guide](no-card-setup-ar.md). The Functions/Blaze deployment instructions below remain a different hosting option and are not prerequisites for the no-card route.

Reviewed 2026-10-18; direct-APK configuration update 2026-10-19. No production deploy, rule publication, real Auth account creation, billing upgrade or production migration was performed. Backend dependencies are pinned in `backend/package.json` and `backend/package-lock.json`.

## Local development

Use Node 22 (verified here: 22.22.2), Java 21 or later for the Firebase Emulator Suite, and the pinned Firebase CLI installed by `npm ci`. Run these commands from `backend/`:

```sh
npm ci
npm test
npm run test:integration
npm run emulators
```

`test:integration` starts Auth, Firestore and callable Functions emulators, executes tests and stops them. It clears **all Firestore records in the demo test project**, so do not run it against an Android acceptance session whose fixtures must be preserved. `emulators` is the persistent development alternative. Both use project ID **demo-strawberry-flutter**, Functions region **europe-west1**, Auth 9099, Firestore 8080 and Functions 5001. The persistent wrapper additionally starts the loopback-only seed helper on 8008. Android emulator reaches the host as `10.0.2.2`; a USB device needs appropriately scoped port forwarding. The demo ID and explicit emulator hosts keep tests separate from production.

The wrapper generates an ephemeral Ed25519 key, writes only its **public** trust definitions to `integration-test-defines.json`, and stores the temporary private key in mode-0600 `.secret.local`. Stop using the wrapper so it can remove that file; remove a leftover file after a crashed session. These keys/certificates are local fixtures and must never be used to license a customer. Never deploy `scripts/seed-helper.mjs` or expose port 8008 publicly. The helper creates only synthetic `@example.test` Auth accounts after checking the exact demo project and loopback emulator environment.

Android synthetic enrollment sends the installation's public `deviceId` and `publicKeySpki` to `POST http://10.0.2.2:8008/seed`. It returns demo tenant/UID/email/password, issuer public keys, project and region. Sending the same device twice within one wrapper session returns the same fixture; another device gets a distinct synthetic tenant. Every wrapper startup generates a validated random 24-character lowercase-hex `TEST_FIXTURE_NAMESPACE`, included in its synthetic tenant IDs. A fresh in-memory server therefore cannot reuse an older on-device database scope/cursor/queue; older local scopes are preserved rather than cleared. The same installation can retain its synthetic UID across sessions. The helper refuses a missing/malformed namespace, a non-demo project or non-loopback emulator endpoints. Alternatively:

```sh
npm run seed:emulator -- /absolute/path/device-public-request.json
```

Do not use multiple persistent wrapper processes: emulator ports, temporary secret file and generated public definitions are session-owned.

## Trusted API and storage contract

Every tenant document and subordinate object lives below `/tenants/{tenantId}`. `backend/firestore.rules` denies every direct client read/write, including all legacy global paths. Flutter uses authenticated callable endpoints; no Firestore write queue competes with the durable SQLite outbox. Admin SDK paths are explicitly authorized independently of rules.

| Callable | Request fields in addition to `tenantId`, `deviceId` | Result / authority |
|---|---|---|
| `bootstrap` | First request has no session; then `challengeId`, P-256 SHA-256 `signature` over returned exact challenge bytes | Verified account, enrolled device, single-use proof; signed entitlement/membership, member projection, server time and one-hour connected session. Disabled own identities may receive a signed disabled certificate, without ledger access. |
| `syncOperation` | `sessionToken`, `operation: {id, entity, payload, expectedRevision: 0}` | Stable receipt `accepted`, `awaiting_approval`, or `conflict`; all financial records are append-only. Employees can send only their own submissions. |
| `pullChanges` | `sessionToken`, `afterSequence`, `limit` (1–500) | Ordered cursor, `hasMore`, server time. Manager feed has tenant records; employee feed contains sanitized parties and that employee's submissions only. |
| `activateLicense` | `sessionToken`, `licensePackage` | Manager redeems issuer-signed paid entitlement. Tenant/user/device/epoch/time checked; replay is idempotent. |
| `createEmployeeInvitation` | `sessionToken`, `uid`, `employeeId` | Manager; existing **verified UID**, active employee record, single-use random invitation, seven-day expiry. Prior Auth refresh sessions revoked. |
| `acceptInvitation` | `publicKeySpki`, `invitationToken`, `signature` | Invited UID authenticated freshly. Signature covers canonical JSON `{domain: "strawberry-accept-invitation-v1", tenantId, uid, deviceId, invitationToken}`. No proof session yet. Inherits existing tenant trial. |
| `setMemberActive` | `sessionToken`, target `uid`, Boolean `active` | Manager changes an employee membership and revokes target refresh tokens. Does not grant manager/platform authority. |

Device fingerprint is SHA-256 of DER SubjectPublicKeyInfo encoded base64url. Device proof uses P-256 with SHA-256 and DER signature, distinct from Ed25519 issuer signatures. `docs/licensing.md` documents issuer packages, trust keys and transfer limits. One-hour session expiration affects online transport, not permitted offline recording.

Financial payload uses integer `totalMinor`, `paidMinor`, `priceMinor` (1/100 EGP) and `qtyMilli` (1/1000 unit); half-up integer multiplication; exact ISO dates; maximum lengths and amounts; no NaN/fractions/string money. Parties carry signed `openingMinor`. No separately mutable opening-balance entry exists. `balance_adjustment` requires a party, positive total, zero paid/quantity/price, `adjustmentDirection` `increase` or `decrease`, and a recorded reason. It changes debt only. Expense categories are retained; employee expense creator attribution remains separate from payroll recipient. Shipment fields on original invoices reference an employee in the same tenant. Post-entry changes use a dedicated immutable `shipment_update` entry: original active invoice ID, positive `shipmentOrder`, required reason/status, optional reference and active tenant shipping employee. All money/quantity/payroll/party/category fields must be zero or empty. A trusted per-invoice `shipmentCounters` sidecar accepts only current order + 1 atomically. Concurrent devices proposing the same order preserve one accepted event and one `shipment-order-conflict`; repeated delivery of the accepted operation never increments the counter again. A conflicting event is provisional evidence, not an accepted latest status. Resolution pulls the current state and creates a new event ID/order; changing a rejected operation payload under its old ID is forbidden. Shipment metadata never changes invoice financial facts or financial totals, and its correction appends another event rather than reversing metadata history.

A server transaction verifies live member/device/tenant, payload and related party/employee/invoice, then creates the immutable record, operation digest/receipt, changes and audit together. Returns use cumulative quantity/value counters and original party/grade/unit/price checks; approval has a single submission lock. Reversals retain history and release reversed-return capacity. Server rejection is a retained conflict, never silent rewriting. Licenses expiring before receipt cause a retryable transport refusal; device timestamps never bypass expiry, and renewal resumes the same queued IDs.

Accepted and conflicting new sync operations share a tenant limit of 600 per minute. Exact duplicate accepted receipts do not create new writes. This reduces authenticated write bursts; it is **not** a financial billing cap or comprehensive DDoS prevention. Bootstrap and read calls still consume resources. Production needs measured usage alerts, quotas and traffic monitoring.

## Production preparation requiring concrete operator approval

Production services are not yet deployed or accepted. As of 2026-10-19, the matching Firebase Android application and release-certificate fingerprints are registered, external client configuration and distinct release/issuer keys are prepared, and signed setup APK version 7 passed local packaging checks. Retain package `com.strawberrytrade.strawberry_trade` and that release identity. Configure verified Auth ownership and trusted enrollment separately; use a separate staging project and a compatible Firestore/Functions location. No client Admin SDK/service-account/issuer private keys are used.

The provisioning and device-transfer scripts in `backend/scripts/` deliberately retain their demo-only guard. A separate [production operator tool](../tools/production-operator/README.md) provides a plan-only default plus an opt-in application module/CLI; its combined local suite passes 30 tests. Application requires a concrete reviewed plan and actual owner approval binding the exact existing verified UID/email, tenant, manually verified phone public key, project-wide refresh-token revocation and original one-time trial. The module rechecks the live owner and tenant history, uses a create-only transaction and the latest valid final-transaction Firestore read time, and records non-atomic Auth/Firestore outcomes for safe retry. The first separately approved enrollment completed on 20 October with four matching documents and its original receipt, without repeating successful revocation. It creates no Auth account and grants no client self-service promotion. Local test success is not execution approval; live evidence is recorded separately. Do not grant manager identity from an email string or create another trial by recreating the same tenant.

Those `backend/scripts/` demo operators share a guard that runs before Admin initialization or user access: the explicit project must be `demo-strawberry-flutter`, **both** Auth and Firestore emulator variables must point to loopback endpoints, and cloud-project environment variables must not identify a different project. A Firestore-only emulator setting is insufficient because Auth would otherwise remain live. The guard has no production override; `npm test` exercises mixed-environment rejection, including actual CLI invocations. Existing synthetic seed-helper restrictions remain stricter and unchanged.

`backend/firebase.production-review.json` is a prepared **Functions-only** configuration. It has no Hosting, Auth or Firestore rule/index entries and excludes local fixture/operator scripts from the function bundle. It has not been deployed or approved. Before using it, check that its seven exported endpoint names do not collide with existing functions in `europe-west1`; a codebase name groups deployment ownership but does not prefix endpoint names. The current server targets default Firestore. Using the existing project safely requires read-only confirmation that deployed rules deny direct access to `/tenants/**` and that no legacy Admin endpoint can bypass that boundary, or a separately implemented/reviewed named-database strategy. Do not publish this backend's deny-all rules over the website's default rules as a connection step.

A production Functions deploy requires **Blaze billing**; emulator development does not. Approval must cover the actual target project, cost estimate, deployment set, rollback and migration closure. This deliverable does not issue an upgrade/deploy command automatically. [Firebase deployment prerequisite](https://firebase.google.com/docs/functions/get-started).

Configure `LICENSE_PRIVATE_KEY_PEM` through Secret Manager, and configure matching server `LICENSE_PUBLIC_KEY_PEM`/`LICENSE_KEY_ID` plus the client's public key ring. The default key ID `local-test-v1` is not a production trust ceremony. Rotate using the issuer guide. Runtime signing of membership is a trusted server privilege; secure the gateway service account and secret-access IAM. APK signing, issuer signing and device keys remain separate.

The operator CLI stores its private PEM encrypted, whereas the current server calls `createPrivateKey(secretString)` without a passphrase. The runtime Secret Manager payload therefore needs the matching server-readable PKCS#8 PEM, protected by Secret Manager/IAM; uploading the encrypted CLI PEM unchanged does not work. Prepare its approved private local import without printing private material or writing it into the project. Only the matching public SPKI PEM, approved key ID and raw base64url client verification key belong in public server/client configuration. The runtime accepts a single active server verification key; account for that when rotating older activation packages even if the APK retains multiple public keys.

The gateway source enforces App Check outside emulators; it has not yet been deployed here. The owner chose direct APK distribution without a Google Play developer account. The current [Android Play Integrity setup](https://developer.android.com/google/play/integrity/setup) permits base API integration by enabling the API in Google Cloud Console without Play Console linking; a paid Play account is not being requested. Linking adds optional controls/reporting and quota-increase eligibility. Do not promise that an unlinked sideload-only project can exceed the documented base quotas.

The authenticated preflight on 2026-10-19 found the Play Integrity and Firebase App Check APIs disabled and this Android provider set to `NO_INTEGRITY`. Configuration and authenticated readback then succeeded: both APIs are `ENABLED`, `tokenTtl=3600s`, `appIntegrity.allowUnrecognizedVersion=true`, and `deviceIntegrity.minDeviceRecognitionLevel=MEETS_DEVICE_INTEGRITY`. Readback returns `accountDetails={}`, meaning the documented default `requireLicensed=false`. The evidence report is `verification/firebase-connection/direct-apk-configuration.json`. This matches Firebase's off-Play guidance and uses a device verdict available without optional Play opt-ins. No billing, global product enforcement, Functions deployment, rules, users or data were changed by this scoped provider preparation. [Official policy controls](https://firebase.google.com/docs/reference/appcheck/rest/v1/projects.apps.playIntegrityConfig), [provider guidance](https://firebase.google.com/docs/app-check/android/play-integrity-provider).

The approved version-8 owner/device bootstrap has subsequent physical-phone evidence: the owner reported home opening, and read-only server checks found matching used challenges and sessions for that UID/device. The production route retained App Check and all existing account/device checks; no raw token was read or logged. The owner also reported offline close/reopen without login. These results do not establish live financial synchronization/retry, phone PDF or update-with-records acceptance. Never ship a debug token, disable gateway checks or make attestation a prerequisite for permitted local saving. P-256 enrollment, Auth verification and tenant authorization remain required; an App Check token alone does not grant access to a tenant.

## Planning estimate before any paid activation

These are USD planning examples, **not a quote or spending limit**. Prices were checked 2026-10-18; region, actual compute duration, repeated synchronization, index/storage overhead and future retention change the bill. Auth here uses email/password, no SMS. There are no attachments, paid analytics, hosting or inventory services in this design.

For one eligible Firestore database the published project-wide no-cost allowance is 50,000 reads/day, 20,000 writes/day and 1 GiB stored data. It is shared by all tenants. Paid backups/PITR are additional. [Firestore billing](https://firebase.google.com/docs/firestore/pricing).

Assume **20 reads and 8 writes per accepted business operation**, including authorization checks, counterparties, receipts/audit/change records and amortized pulls. This is a deliberately rounded model, not an emulator billing measurement; retries, reviews and initial downloads add work. The pricing page's displayed default rates at review were $0.03/100,000 reads and $0.09/100,000 writes; replace with the approved location's actual SKU before launch. [Location pricing](https://cloud.google.com/firestore/pricing).

| Usage example, 30 days | Database activity model | Illustrative database operation cost |
|---|---|---|
| Pilot: 10 businesses × 100 operations/day | 20,000 reads/day; 8,000 writes/day | $0 in read/write charges if this is the eligible database and quotas are otherwise unused. Allow roughly **$0–10/month** for a small pilot including incidental services; this is not guaranteed. |
| Larger example: 100 businesses × 500 operations/day | 1,000,000 reads/day; 400,000 writes/day | After daily free quotas: 28.5 million reads/month and 11.4 million writes/month; **$8.55 + $10.26 = $18.81/month** at those illustrative rates, before compute/storage/traffic/secrets. Plan roughly **$25–75/month** until actual load measurements replace the assumptions. |

Storage grows permanently with ledger, audit, receipts and change feeds. At an assumed 8 KiB stored per operation, the pilot adds about 234 MiB/month and the larger example about 11.4 GiB/month before index overhead. Do not delete receipts or history casually to reduce cost: doing so can break exactly-once retry and initial replay. Retention/compaction needs a separately reviewed protocol.

Functions has published usage-based compute/network charges and a no-cost usage allowance; build images, Artifact Registry and secret accesses can also incur small charges. [Firebase pricing](https://firebase.google.com/pricing), [Secret Manager pricing](https://cloud.google.com/secret-manager/pricing). Inference: for a small cold-starting workload these ancillary charges may be modest, but no latency/compute billing benchmark was performed. Budgets notify; they do not inherently stop usage. Configure owner-approved alerts and inspect real staging metrics before approving a production budget.
