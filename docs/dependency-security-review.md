# Dependency security review — 6 November 2026

The compatible backend's production dependency audit is **PASS: zero reported vulnerabilities** for both backend and Worker. This is a dated registry result, not a claim that every dependency is free of defects. The complete backend developer-tool audit remains **FAIL: 11 moderate findings, zero high/critical findings** in Firebase CLI dependencies. The complete Worker developer/runtime audit is **PASS: zero reported vulnerabilities**. No service was deployed and no production account or record was accessed during these tests.

## Installation and remaining developer-tool limits

`npm ci --ignore-scripts` returned zero even when temporary registry/archive fetch failures silently omitted optional platform binaries. A zero install exit code alone is therefore insufficient. Reifying the same locks with `--include=optional --fetch-retries=2 --fetch-timeout=120000` recovered the locked Linux workerd/esbuild packages without changing package or lock hashes. Verify `workerd --version`, `esbuild --version`, and `wrangler --version` before packaging. The deployment packager now performs these checks. Do not use a missing executable as evidence that Node 22 is incompatible.

The final actual `npm ls` [backend tree](../verification/continuation-2026-11-02/final-review/dependency-backend-workspace-npm-ls.json) has no reported problems. The [Worker tree](../verification/continuation-2026-11-02/final-review/dependency-worker-final-npm-ls.json) exits zero but reports two extraneous optional WASM artifacts (`@emnapi/runtime`, `@img/sharp-wasm32`) after npm's optional reification; these artifacts remain declared in the lock and were not deleted. This is recorded separately from the zero registry audit result. Native executable and actual HTTP acceptance remain mandatory. Earlier transient audit/invalid-tree failures remain as separate evidence; the successful final audit supersedes them for the same immutable package hashes.

The eleven remaining backend findings are inherited through development-only `firebase-tools@15.34.0`: `glob@10.5.0` / `minimatch@9.0.9`, `uuid@9.0.1`, and `@opentelemetry/core@1.30.1`, plus their parent packages. The [OpenTelemetry advisory](https://github.com/open-telemetry/opentelemetry-js/security/advisories/GHSA-8988-4f7v-96qf) requires core 2.8.0; the [UUID advisory](https://github.com/uuidjs/uuid/security/advisories/GHSA-w5hq-g745-h8pq) requires 11.1.1 or later for the affected release line. Glob's available fix similarly requires a new major. These are not safe semver patch updates to the old CLI graph. The CLI reads local project paths and is excluded from production dependency installation; the current application does not expose developer glob patterns or UUID output buffers as a customer API. This limited reachability review is not a proof that every Firebase CLI command is unaffected.

Remaining engineering: upgrade to an upstream Firebase CLI release with compatible patched transitives, or separately review the major API changes and test the affected deployment/emulator commands before adding scoped development overrides. Until then, do not report the complete developer-tool audit as zero. Production gateway deployment, rollback metadata verification, provider acceptance and client handover remain separate readiness requirements; these dependency results authorize none of them.
