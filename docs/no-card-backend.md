## Architecture and authority

The front Worker forwards to one constant named Durable Object. It must not select arbitrary objects from a caller-supplied tenant/device identifier. The object is a runtime boundary, not the financial database: it holds disposable Admin SDK clients and token caches. Firestore remains authoritative for tenant membership, device public keys, challenges, proof sessions, licenses, audit, return/review locks and exactly-once operation receipts. All financial writes continue through `createGateway`; the HTTP adapter does not grant direct client database access.

The external callable-compatible adapter is `backend/src/http-gateway.mjs`. Before invoking one of the seven allowlisted methods it verifies the App Check token and exact expected Android app ID, then verifies the Firebase ID token with revocation checking. The original live user/member/device/session/license checks still run inside the gateway. `acceptInvitation` retains its verified-account, invitation and device-proof checks. An incoming JSON `auth` or role field is never an authentication context.

The adapter enforces HTTPS outside its guarded local demo, JSON POST, a 64 KiB streamed-body limit, bounded nesting, and safe decoding of the native callable integer tags. It returns the callable result/error envelope expected by FlutterFire. Public errors do not include provider payloads, tokens or keys. Firestore quota exhaustion returns retryable `RESOURCE_EXHAUSTED`; unavailable/deadline errors return `UNAVAILABLE`. These responses do not acknowledge or discard a queued financial operation.

The optional compiled `GATEWAY_BASE_URL` uses FlutterFire's `httpsCallableFromUrl`, retaining SDK Auth/App Check token handling. The operator config tool accepts `--gateway-url`; matching Dart/Node validation rejects credentials, queries/fragments, ambiguous paths, insecure production URLs, IPs and local/reserved hosts. No new URL is silently injected into the already-built version-7 APK. An empty setting retains the original callable/emulator route; a no-card release needs the approved external URL explicitly configured.

## Runtime compatibility

Workers is not an unrestricted Node process. Firestore's normal gRPC route is unsuitable; the tested candidate uses `initializeFirestore(..., {preferRest:true})`. It also requires a pinned compatibility layer for Google gax/protobuf startup compilation and error decoding. A bundle that merely imports successfully is insufficient. Review the worker package's exact dependency lock and compatibility code, and rerun real workerd tests after dependency or compatibility-date changes. Do not permit arbitrary request-time evaluation to make a dependency run.

Heavy gateway work belongs inside the Durable Object. Current official limits give it 30 seconds of CPU per invocation; the front Worker still has the Free plan's 10 ms allowance. The object must use a `new_sqlite_classes` migration, since legacy key-value Durable Objects are not the Free-plan choice. This is compute routing; no financial SQL storage or data migration is introduced. [DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/), [Free eligibility and quotas](https://developers.cloudflare.com/durable-objects/platform/pricing/).

## Quotas and acceptance

Workers Free currently permits 100,000 front requests/day. SQLite Durable Objects have a separate 100,000 requests/day and 13,000 GB-s/day allowance. At the documented 128 MB allocation, a single continuously active object would consume `86400 × 0.128 = 11059.2 GB-s/day`; this is a planning inference for one object with no competing account usage, not a measured bill or service guarantee. The front/DO also retain startup, subrequest and connection limits. Cloud acceptance must measure the actual pinned bundle's startup, busiest transaction/retry paths, response sizes and account usage. Do not activate a paid plan to make a test pass. [Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/).

Firebase Spark's shared daily operation and storage quotas remain binding, including usage by the old website. Reaching a free quota can make synchronization unavailable. The native ledger and outbox retain permitted offline work, then retry the same operation IDs when service returns and authority permits. There is no claim of unlimited free commercial capacity, guaranteed availability, instant offline revocation, or automatic archival/deletion to bypass storage quotas.

Local real-runtime and emulator checks must be reported separately from a published endpoint, real App Check attestation and a production phone test. The existing native/host acceptance of the original gateway does not establish those new outcomes automatically.

## Credentials: a separate concrete approval

No Google service-account key has been created or exported for this candidate. No documented automatically issued per-Worker OIDC workload identity was established, so do not claim keyless Google federation. The proposed deployment needs a dedicated, reviewed runtime service account and protected host secrets unless a concrete keyless solution is demonstrated.

Review the minimum Firestore transaction/read/write and Auth user-read/session-revocation permissions actually used by the gateway. Do not use an owner credential, CLI OAuth refresh token, Editor/Owner role, or an administrative key copied from another application. Firestore IAM is not a document-path substitute for Rules: an Admin credential for the shared default database can affect legacy data if compromised, even though application code checks `/tenants/...`. This blast radius must be explicit in the deployment review; do not describe it as tenant-limited IAM.

The dedicated Google credential and Ed25519 issuer private material belong only in Worker secrets. Validate each actual value against the platform's secret-size limit before upload. Keep APK signing, license issuing and phone identity keys separate. The issuer private/public key pair and key ID must match the APK's public trust ring. Never put private material in `.dev.vars` included in source archives, Dart defines, APK assets, terminal output or chat. Preserve encrypted off-device backups and password recovery independently.

## Deployment and rollback boundary

Before publication, record the owner's Cloudflare account, Free-plan eligibility, exact script/SQLite class and constant object name, approved HTTPS URL, Firebase project/database/app ID, source/lock hashes, dedicated service account and permissions, secret names and public key fingerprints. Confirm existing endpoint names and old Admin services do not bypass new tenant boundaries. Publish neither the new deny-all Firestore rules nor a legacy migration as part of changing compute hosts.

Employee synchronization also requires the `employeeChanges` composite index on `uid ASC, sequence ASC` with `queryScope: COLLECTION`, declared in `backend/firestore.indexes.json`. A read-only live inventory on 20 October 2026 (Cairo) confirmed that this index is absent from the current default database. Emulator query acceptance does not prove production index availability. Prepare an additive creation of this one index, separately reviewed and approved; wait for its READY state before employee acceptance. Do not deploy the whole indexes file over the existing website's configuration, remove its indexes/field overrides, or publish rules as part of this step. Runtime IAM must not include index-management permissions.
