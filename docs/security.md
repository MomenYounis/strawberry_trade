# Security assessment and operational limits

Assessment dates: 2026-10-18–19. Scope: the independent Flutter application, Kotlin security channel, trusted issuer utility and tenant-scoped Firebase gateway in this deliverable. The earlier website was inspected as migration evidence; it is not embedded in the APK. This document is a source-level threat assessment, not a claim of penetration-test certification. Test execution and Android/emulator evidence must be read together with the delivery test report.

## Assets, actors and boundaries

The protected assets are tenant financial ledgers, pending operations, employee/private payroll information, counterparty details, audit records, user credentials, installation keys, database passwords and issuer authority. Relevant adversaries include a member of another tenant, an employee attempting manager actions, a manager attempting platform-level license issuance, a person with a copied backup/package, a malicious imported file, a device thief, and a user controlling a modified/rooted device.

The Android process, local encrypted database, Firebase Auth, trusted gateway and operator issuer are distinct boundaries. Tenant IDs, copied device IDs, client roles, client timestamps and a hidden button are not authorization. A valid Firebase token alone is insufficient: the server checks verified account status, revocation, tenant membership, enrolled device, possession proof and a scoped online session. Offline authorization uses previously trusted, signed membership and tenant entitlement. Its inability to learn a new remote change while disconnected is explicit.

## Findings reproduced from the legacy implementation

The source copy remains unchanged. Specific legacy findings were verified by reading the actual implementation:

| Severity | Evidence | Result in this implementation |
|---|---|---|
| Critical | Legacy `backend/firestore.rules` grants managers access to shared `/members`, `/managerData`, `/directory`, `/submissions`, `/reviews` and `/audit` without a tenant boundary. | New data lives under `/tenants/{tenantId}`. Client Firestore rules deny every direct read/write. The callable gateway independently checks each tenant, member and device, including Admin SDK paths. The old production paths are not closed automatically; migration/deployment remains an operator review step. |
| High | Legacy `backend/scripts/provision-member.mjs` looks up an existing email and writes membership without verifying account ownership. | Trusted provisioning accepts an existing verified UID and revokes prior refresh sessions. Employee invitations bind UID, employee record, fresh authentication, a single-use token and P-256 installation proof. An email string or invitation alone cannot create a manager/platform administrator. |
| High | Multiple manager forms call `saveState()` and display success/close without checking its false return; legacy synchronization rejects writes until initial loading completes. | The Flutter controller requires an opened local store and valid authority, awaits a SQLite transaction and reports success only after commit. Repeated form saves reuse a stable draft operation ID. Storage and readiness failures keep the form available. |
| High | Legacy backup validation accepts inconsistent invoice totals/paid amounts and does not require return grade/unit to match the invoice. | Dart ledger/import validation checks fixed-point totals, payment bounds, return identity/grade/unit/price and cumulative quantities/values. Backend validates the same invariants transactionally. A manager cannot bypass validation with a direct Firestore write. |
| High | Legacy manager-record rules accept generic record shapes and allow independent financial writes without mandatory audit coupling. | New trusted mutations create immutable records, idempotent receipts, return/review locks, change feed and audit in one server transaction. Local operation/outbox/audit changes commit together. Corrections preserve financial history through reversals. |
| Medium | Legacy payroll history reads `employee.monthlySalary` for every historical month. | Effective-dated salary terms provide historical evidence. Missing historical terms are not fabricated during migration. |
| Medium | Legacy employee review displays omit counterparty names; rapid submission taps can allocate distinct IDs. | Submissions preserve counterparty name and facts; server derives the canonical directory name. Review screens show the counterparty, and guarded saves retain the original draft ID. |

These fixes apply to the new implementation. They do not retroactively secure an unchanged deployed website or shared legacy database. Close old endpoints/paths only after reviewed migration and rollback validation. No rules or Functions were deployed to production as part of this assessment.

## Implemented controls and evidence

| Boundary | Implemented control | Evidence / practical limit |
|---|---|---|
| Tenant and role | Server derives member authority from the authenticated UID; all paths are tenant-scoped; employee feeds contain redacted directories and only their own submissions. Local stores bind tenant, UID, role and employee record. | `backend/src/gateway.mjs`, `backend/firestore.rules`, `lib/data/ledger_store.dart`. Tests must include guessed IDs and actual employee payload inspection, not just UI visibility. |
| Account ownership | Verified Auth account, refresh-token revocation cutoff, fresh invitation authentication and no manager promotion by client. Existing memberships are not silently relinked. | `backend/src/enrollment.mjs`. This identifies control of the account, not the real-world uniqueness of the person. |
| Device possession | Non-exportable P-256 private key generated by AndroidKeyStore; server signs no membership merely from a copied fingerprint. Bootstrap uses a single-use random nonce, domain, UID, tenant, device and expiration. | Kotlin `MainActivity`, Dart `DeviceSecurity`, backend bootstrap. The public key certificate is self-issued identity, not Android hardware attestation. |
| Online session | Proof session token binds UID, tenant and device; client transport also binds the current Auth UID/device and detects identity changes during bootstrap. Session expiry affects connected synchronization only. | `lib/services/gateway.dart`, backend authority checks. It is not an offline verification lease. |
| Licensing | Ed25519 signatures, explicit issuer key IDs, exact schemas, size limits, canonical base64url/JSON, tenant/user/device bindings, monotonic epochs, exact trial dates. | `lib/security/licensing.dart`, issuer tests and Node-to-Dart fixture test. No default production trust anchor, private key or editable activation flag. |
| Tenant activation | Paid packages enter durable encrypted pending state with local acceptance. Synchronization obtains a proof session, checks live disablement, redeems the tenant entitlement, obtains fresh certificates, then clears pending state only after confirmation. | `lib/security/license_sync.dart`; tests cover disconnection, restart and stale trial/bootstrap ordering. Employee transfers do not gain issuance privileges. |
| Revocation | Signed disabled certificates override locally imported pending paid authority. Firebase's explicit `user-disabled` response persists a scoped disable lock. Ordinary network/auth-token expiry does not erase data or disable allowed offline entry. | Bootstrap and `LicenseSession.recordAccountDisabled`. Remote changes cannot reach a disconnected phone instantly. A successful fresh trusted bootstrap is required to clear the account lock. A live signed role change locks the previously opened role-bound local store and requires reviewed re-enrollment instead of reusing its cached authority. |
| Local database | SQLCipher primary store; each account/tenant has a random 256-bit password, AES-GCM wrapped with a non-exportable AndroidKeyStore AES key. App code checks `PRAGMA cipher_version` and fails closed without encryption. | `lib/data/ledger_store.dart` and native channel. Desktop SQLite tests use an explicitly unencrypted factory; only actual Android integration can prove SQLCipher on Android. The password necessarily enters app memory while opening the DB. |
| Key loss | Protected files are in `noBackupFilesDir`; absent keys over existing ciphertext fail closed instead of silently replacing the installation identity. No IMEI or uninstall-survival assumption. | Kotlin key creation and AES-GCM decrypt paths. Trusted re-enrollment and scoped ledger restore are required; a copied database is not a license. |
| Time | Persisted high-water reference, sleep-aware monotonic elapsed time, boot counter, expected wall baseline and suspicious-reboot lock. Reimport cannot erase rollback evidence; offline files cannot repair suspicious reboot. | `trusted_clock.dart`, licensing tests. Across reboot, sub-reference OS manipulation/root/state rollback cannot be completely defeated offline. |
| Durable sync | One SQLite outbox, stable IDs, transactional local commit, server receipts/digests, session-generation checks and tenant/user-bound acknowledgments. The SDK callable response is a server response; there is no second independent Firestore client write queue. | Controller, store and gateway tests. Force-stop prevents work until the next real launch/foreground/background execution opportunity. |
| Imports | File-size cap before decoding, exact authority-free backup schema, scoped tenant/user restore, relationship validation, consistent accounting, stable queued IDs and transaction rollback on failure. | Backup restore tests in `test/store_test.dart`; no credentials, membership, license, device keys or accepted authority are imported from a ledger backup. |
| SQL/file handling | SQL values use binding parameters and table/entity names are fixed. File picker access does not execute code; channel scopes are length checked and hashed to internal filenames. | `ledger_store.dart`, native channel. Very large permitted files can still cause memory pressure; the importer is not a streaming parser. |
| Android components | Backup disabled; explicit cloud/device-transfer exclusions; native secrets use no-backup storage; cleartext traffic disabled in main manifest. Application source exports its launcher without financial intent handling or app links. | Packaged debug APK version code 4 was inspected: debug/cleartext enabled for local emulators, backup disabled, compiled cloud/transfer exclusions, four non-exported providers with cache-limited share paths. Five components are exported in the merged APK: launcher, two Firebase Auth callbacks, a permission-protected Google revocation service and a DUMP-protected profile receiver. It is inaccurate to call the launcher the APK's only exported component. This inspection does not prove SDK callback runtime validation or release flags; final artifact identity and any later inspection belong in `test-results.md`. |
| Exports and logs | Manager-only reports/backups, sanitized employee feed, CSV formula-prefix neutralization, Arabic error mapping. Backend logs endpoint/error class only; security channel returns generic Arabic failures. | Export/store/gateway code. Shared files are deliberately readable output and remain sensitive after leaving the app. |

## Issues found during the new implementation and resolved

1. A replayed package originally reanchored the wall baseline. Rolling the wall clock back, reimporting that package and rebooting could discard evidence of the rollback. The anchor now preserves the current accepted time and expected wall baseline; regression tests cover the sequence. A suspicious reboot can be repaired only using a fresh authenticated bootstrap, never a transferable file.
2. Manual paid activation originally updated only the local device. The next server bootstrap returned the old trial, causing epoch rejection and preventing business-wide activation. Paid activation now has a durable pending redemption and explicit server activation step before accepting the refreshed entitlement. Failure/restart tests demonstrate retention.
3. Live member/device disable originally failed bootstrap before sending a certificate, leaving the client unaware that its stored authority had been revoked. Own-identity proof can now receive a signed disabled certificate without receiving ledger access. A disabled old server entitlement also overrides a newer unredeemed offline paid package. Explicit Firebase Auth account disable is persisted separately because Auth can prevent any bootstrap.
4. An in-flight activation acknowledgment could clear the durable retry marker of a newer package imported during the request. Acknowledgments now compare the exact pending signed package. The issuer registry also rejects trial-date resets at higher epochs and paid-to-trial replacement. Its protected-output check resolves existing parent symlinks, preventing an apparently external key path from writing into client files. A fresh trusted response can repair a reboot baseline without ever decreasing accepted time. Regression tests exercise each boundary.
5. Gateway proof sessions were initially bound locally only to tenant. They now also bind UID/device and reject a changing Auth identity before updating the transport session. Controller generation checks prevent late responses from acknowledging another session's queue.
6. Android `allowBackup=false` alone does not disable every manufacturer's device-to-device transfer behavior. Explicit extraction-rule exclusions were added in addition to keeping protected state in `noBackupFilesDir`.
7. A very long decimal input could overflow a native Dart integer during scaling before the maximum-amount check, potentially becoming a smaller accepted value. Untrusted digits now parse and scale as `BigInt`, are checked against the fixed accounting limit, and narrow to `int` only afterward. Regression inputs include Arabic digits, wraparound values, long strings and the exact permitted boundary. This closes the local input path rather than relying on later server rejection.
8. An open statement/export/form route could outlive its account after sign-out or an identity transition. The root `MaterialApp` is now keyed by tenant, UID, role, employee and readiness, replacing the navigation stack on that transition. A widget regression opens a private statement with a known balance, ends the account, and verifies the previous route and navigator are removed. Live revocation also hides the entire navigator and invalidates old store handles without deleting the pending queue.
9. Filtering a ledger to the report window before calculating reversals could miss an original record outside the window; applying all later reversals could also rewrite historical periods. Reports and Arabic statement text now derive dated effects from the complete scoped ledger before selecting the requested period, including dated returns, reversal effects and payroll/business categories. Known-ledger regressions compare monthly results, total cash movement and opening/closing balances. Budget targets are scoped local preferences with validated, authority-free backup keys; a stale budget dialog cannot write to a replacement account.
10. Production callable enforcement requires an initialized App Check client as well as server configuration. The source now pins `firebase_app_check 0.5.0` and initializes Play Integrity only for production connected setup/synchronization. No debug provider or debug token is shipped by this code path, and local database opening/allowed commits do not wait for attestation. The Android app and release-certificate fingerprints have now been registered and signed setup APK version 7 passed local packaging checks; live device-token acceptance remains unverified. Firebase initialization also binds the expected default app/project and rejects configuration mismatches rather than silently reusing another project.

## Remaining risks and release conditions

| Severity | Remaining condition | Mitigation and limit |
|---|---|---|
| High until live acceptance | Local release/issuer keys and Android registration are prepared; signed setup APK version 7 passed packaging verification. Production attestation, trusted enrollment and backend acceptance remain outstanding. | The owner-controlled private keys stay outside source and APK; passwords are in the desktop secret store. Keep signing, issuer authority and attestation separate. An emulator/debug acceptance result is not production-service acceptance. |
| High | Modified/rooted devices or compromised issuer/server administration can defeat local controls or read process memory. | Server authorization and accounting remain authoritative. Hardware-backed Keystore is device-dependent and is not claimed universally. There is no claim of absolute offline tamper resistance. |
| High until device acceptance | Cloud-only direct-APK App Check configuration and readback succeeded: both relevant APIs are enabled; the app policy permits off-Play recognition/licensing and explicitly requires `MEETS_DEVICE_INTEGRITY`. A physical token and protected bootstrap are still unverified. No paid Play account was created. | Preserve the registered release certificate and verified policy, then test a real signed-phone token plus protected bootstrap. Do not ship debug tokens or disable authorization. Attestation is not a prerequisite for permitted local recording. |
| Medium | A newly revoked phone or employee can continue previously permitted offline work until authenticated information arrives. | Known expiration is enforced locally; new revocation is eventual. The server rejects disabled/expired submissions on receipt and preserves the queue for operator resolution. Device transfer cannot instantly disable the disconnected source. |
| Medium | Backup JSON, PDF and CSV exports are readable after sharing. | Export is manager-only with an Arabic privacy warning. Store/share only with authorized recipients and protected storage. This version does not claim passphrase-encrypted export files. App-private encryption does not encrypt user-shared documents. |
| Medium | An unlocked phone can expose an already authorized offline session to its holder. | Use Android screen lock and device access controls. Keystore signing/wrapping here does not require per-operation biometric authentication; that choice preserves unattended/offline availability and is not described as biometric security. |
| Medium | Offline elapsed time across reboot relies on wall progress; a sufficiently controlled wall/state rollback may be undetectable. | Preserve authenticated checkpoints and fail closed on detected rollback. Re-enrollment preserves original tenant trial. Do not market this as a secure hardware clock. |
| Medium | Issuer CLI registry is local to a trusted issuing machine. | Maintain one authoritative registry and encrypted backups. Parallel independent registry copies can over-issue. `--replace-device` changes the issuing registry and does not itself revoke the server device. |
| Medium | Legacy website/rules remain unsafe for independent tenants until reviewed migration and closure. | Never onboard a second business to the old shared paths. The Flutter deployment artifacts do not automatically modify production. |

The current [Android setup](https://developer.android.com/google/play/integrity/setup) explicitly supports enabling the base Play Integrity API through Google Cloud Console; Play Console linking is recommended for additional capabilities and quota increases. Firebase's [off-Play policy](https://firebase.google.com/docs/reference/appcheck/rest/v1/projects.apps.playIntegrityConfig) allows unrecognized versions and non-Play licensing while requiring an explicit device-integrity verdict. `NO_INTEGRITY` is not an acceptable accidental default for this combination. Only the two APIs and this Android app's provider policy were changed, with authenticated readback saved in `verification/firebase-connection/direct-apk-configuration.json`. The returned empty account-details object represents the documented default `requireLicensed=false`. No global product-enforcement change, paid-account creation, database rule replacement or production financial write occurred in that step. Keep Auth/member/device proof checks in addition to attestation. Cloud-only configuration is not evidence of a passed token exchange.

Android developer-identity registration is a separate evolving distribution requirement. Its 2026 rollout initially covers certified Android devices in four named countries, with global expansion planned for 2027. Do not claim that direct APK distribution permanently avoids every Google registration requirement; recheck actual target regions/channels before expansion. [Official rollout](https://developer.android.com/developer-verification).

The delivery test report records the actual emulator, PDF, persistence/update, manifest and host multi-season/full-storage evidence and its limits. Those categories must not all be presented as unexecuted simply because production acceptance remains open. Remaining production conditions include physical-phone loss/restoration and clock/reboot acceptance, final signed-release update verification, production App Check and certificate verification, and a reviewed migration rehearsal. Host SQLite storage exhaustion is not a physically full Android phone; a fake clock is not a device reboot, and a debug manifest inspection does not establish a release manifest.

No remote messages, user accounts, billing upgrade, paid service activation, production data migration or production deployment are authorized by these artifacts alone. Trusted operator actions remain concrete, reviewable separate steps.
