# Annual archiving design and implemented boundary

Updated 2026-11-07 (Africa/Cairo). The implementation described here is the v12 continuation; signed app source is `7058f24b2a85218fb96d88e435e0d3c5fce0e1c8`. Backend/private-runtime file inventories identify their separate working-tree inputs. [Readiness](commercial-release-readiness.md) is the authoritative PASS / FAIL / BLOCKED / NOT RUN ledger and release identity.

**Scheduling, automatic financial closing and cleanup remain disabled.** The concrete annual engine, prospective salary correction, bounded snapshot installer, portable recovery, storage adapters and recovery quarantine now exist locally. Their local tests do not qualify production storage, keys, provider consistency or complete disaster recovery. Annual archiving remains part of the requested deliverable.

## Model and effective dates

The APK keeps a scoped SQLCipher local ledger/outbox. Firebase Auth/App Check and device-proof sessions authorize a Worker forwarding to a singleton SQLite-class Durable Object. That object hosts the Firestore Admin SDK gateway; it does not hold a separate ledger database per business. Business isolation uses logical `/tenants/{tenantId}` paths in the existing shared Firestore database/project. Direct Firestore client rules deny all access; the Admin SDK gateway enforces its own authority.

Africa/Cairo civil dates define `[September 1, next September 1)`. The first annual package is 2026-09-01 through 2027-08-31; first eligibility is Cairo 2027-09-01 00:00. `archive-calendar.mjs` uses IANA timezone conversion from trusted server milliseconds. No hardcoded UTC offset or phone-clock authorization. Date-only business fields select a year by their literal validated civil date. Current postings use `date`; corrections also retain `originalBusinessDate`. New authoritative changes record `acceptedAtMs`, tenant `sequence` and closing version. Historic acceptance times/client creation times are not invented where absent.

Default proposed UTC cadence is `17 * * * *`, hourly minute 17, normally 00:17 Cairo September 1 under current September DST. Future offset changes are handled by the Cairo gate rather than annual UTC constants. See operations for missed invocation/backlog handling. No runtime cron is installed. `selectArchiveYears` recovers already started runs, reports unstarted missed years and requires explicit ordered administrator selection; no archives before first year.

## Consistency, closing and fencing

`ArchiveStateStore` with `FirestoreArchiveStateAdapter` reads tenant root and `/archiveRuns/{year}` in a bounded transaction. `checkpoint()` requires explicit trusted close/export authorization, active tenant, eligibility and prior-year verification. It captures root sequence C and closing version V while setting the closed-through boundary on the same root that every financial acceptance transaction reads/updates. Concurrent acceptance serializes with that checkpoint. Subsequent accepted operations receive sequences after C; new-year trade is not locked during export.

`immutableChangesAtCheckpoint` reads bounded ordered pages with `sequence > cursor AND sequence <= C`. Each sequence must be contiguous through C. Accepted financial/directory facts are immutable; submission state changes append full new change payloads. A private SQLite projection replays this frozen feed to reconstruct submissions as they stood at C. After a prefix is removed, the archive source factory requires an injected trusted seed provider; it accepts only a live branded manager snapshot projection, then reads contiguous deltas after its checkpoint through annual C. The snapshot seed validates a separately trusted header digest, every page, final descriptor digest, record identities and scope before receiving that brand. Paginating live mutable collections is never used as a snapshot. Root/manual administrative writes outside the gateway are outside this proof; migration/provisioning/audit metadata required for a whole-system backup must be retained separately. The source reader refuses missing history or rewritten immutable IDs.

Each lease has owner, expiry and a monotonically increasing fence. Every authoritative checkpoint/progress/publication/verification transition checks the current persisted fence and expiry. A stale process may finish an immutable object upload, leaving an unreferenced object, but cannot publish the pointer or advance the job. Tests replace an expired runner and deny stale checkpoint, publication and advancement. No unbounded transaction spans export/upload.

Supported durable states are `eligible -> checkpointed -> exporting -> uploaded -> verified -> cleanup_pending -> pruning -> complete`. The final two states are implemented only by the private conditional manager-`changes` pruner described below; no production cleanup has run. `cleanupBlockers` requires conditional plan/snapshot evidence rather than reporting an absent pruner. Retry classifications/time, chunk progress, manifest pointer and verification evidence are stored separately. Close version increments once per tenant/year. Export retry does not create another close.

## Default closed-period policy

Owner review is required before enabling this policy. Historical reopening/restatement is excluded. Late accepted-transport financial submissions become durable `lateOperations` with full original operation/payload/digest/ID, original business date, actor, server receipt time, reason, close version and `needs_review`; no financial entry, approval or sequence is created. Receipts explicitly distinguish transport retention from financial acceptance. Client outbox evidence is retained, blocked from automatic retry, exposed for manager review and excluded from displayed financial effects after the hold is known.

Pending employee submissions remain pending. Rejection remains nonfinancial. Old-date approval is held; an explicit manager correction posts matching financial facts in the current Cairo open period with a new immutable entry ID and linked original operation. Original business date and posting date remain separate in source, local columns, reports, CSV and PDF. A transactional correction lock makes this exactly once, including retries and another device attempting a second correction. A repeated historical view has no posting path.

Backdated salary terms are held without creating the historical salary term or month lock. The manager can now resolve held evidence as a prospective term for the current Cairo month, retaining the same employee/rate and an explicit reason. The original historical month and its obligations remain unchanged. The reason is a top-level operation field preserved by ordinary controller sync, encrypted backup and exactly-once server audit/linkage. This is a prospective policy, not a historical salary restatement; owner policy acceptance remains required before closing.

`annual-catalog.mjs` requires a dated opening plan bound to tenant/year, actual party hashes and checkpoint sequence. Missing effective dates or an opening effective within the proposed closed interval refuse closing. No creation timestamp or guessed date is substituted. A real within-period opening needs a separately reviewed dated-posting migration; this implementation does not silently reinterpret it.

Production deletion eligibility is **NONE under the current disabled defaults and unaccepted recovery/storage gates**. Local code can conditionally remove duplicate manager `changes` documents only. All other collections remain retained; this is not permission to delete records by age.

Residual online storage is intentional. No production documents were deleted and no actual storage savings have been measured or claimed. Conditional feed removal would retain all original financial facts, receipts and employee feed. Five businesses still share project/account quotas. ## Accounting controls and immutable package

`archive-projection.mjs` is private Node tooling using isolated SQLite, not imported by the Worker. It reconstructs the source with BigInt accounting. Source controls and strict reader controls separately include sorted role/account openings, period effects, closing balances, signed receivables/payables, payroll paid-by-month/known obligations, period totals, period and cumulative recorded cash movement, pending submission count, snapshot/source counts and identity digest. Ordering uses explicit code-unit comparisons; locale-specific collation must never affect identity or resumability. English/Turkish subprocess regressions cover mixed-case IDs. Hand-calculated fixtures assert the actual values. Carried values are baselines, never financial postings. Active reports still use complete history; no double-baseline install is performed.

Format/schema version 1, archive protocol 2 (separate from negotiated sync protocols 1 and 2). Context includes tenant/year/run ID, sequence/version, prior manifest hash, key ID and creation time; interval is explicit Cairo civil half-open dates. Canonical manifest body records algorithm/version, ordered chunk descriptors, plaintext/ciphertext SHA-256, byte lengths, counts and controls. HMAC authenticates the manifest; ciphertext chunks use established Node AES-256-GCM with random 96-bit nonces and separate per-run/per-index HKDF-SHA256 keys. Tenant/run/key ID and purpose bind key derivation; context/index bind AAD. Master key bytes are caller-supplied private runtime material and never enter source, ordinary manifests, APKs or logs. No production archive key was created. Rotation uses new key IDs/runs and retained recovery ability for old keys; provider re-encryption alone does not rotate archive encryption.

The manifest is authenticated plaintext metadata: its controls include account IDs and balances. Chunk encryption does not hide those controls. Treat manifests and run evidence as private financial data under the same restricted storage/access boundary; do not publish them as harmless hashes. A requirement to conceal financial controls from the storage provider would need an additionally encrypted manifest envelope and separate authenticated discovery metadata before acceptance.

Resume authenticates every reused ciphertext chunk with the supplied key and full context, then compares the exact decrypted plaintext with the replayed source before appending objects or publishing. Matching ciphertext hashes alone are insufficient. A changed master key or key ID fails while the persisted run remains `exporting` with its original progress; retrying the original key can complete. Rotation during an existing run is unsupported. Two coordinator regressions prove this recovery property.

Limits: default 64 KiB chunks, maximum 128 KiB, record 24,000 bytes, manifest 512 KiB, at most 1,024 chunks/64 MiB ciphertext and 500,000 records. Progress documents cap at 500 KB, below Firestore's 1 MiB document limit. Accounts cap 10,000 and payroll months 20,000; manifest size may impose a smaller practical envelope. All limits fail closed. The current prepared-source fixture exported/restored 73,000 entries in 575 chunks using 731 source queries; growth to 80,300 used 632 chunks/804 queries and 167,304 KiB maximum RSS. These private Node measurements exceed the Worker memory envelope and do not qualify a Worker annual job. Peak annual volume/long notes can exceed package limits. The retained manager-snapshot seed now avoids requiring already pruned prefixes, but source reconstruction remains bounded and requires production runtime/capacity acceptance.

The concrete `annual-engine.mjs`/`annual-catalog.mjs` pipeline connects bounded Firestore inventory, approved year selection/opening evidence, fenced closing, encrypted resumable source preparation, streamed private Node export and independent restore. Construction performs no I/O. The source is read once during the uninterrupted preparation pass at fixed C; authenticated linked pages retain O(1) progress. A restarted invocation validates/replays saved pages into private SQLite. It does not repeatedly query the whole Firestore prefix for every four chunks. The older bounded `runArchiveExportStep` primitive remains available but is not the selected efficient annual execution path.

Runtime/deadline checks every 128 work units and lease heartbeats span source/seed/projection/control scans. They are cooperative checks, not a guarantee of OS preemption. Expired or replaced leases cannot publish. Shared quota reservations include bounded transaction retries, immutable collision reads and mirrored storage work; exhaustion retains progress. A final reservation-overhead regression is tracked in readiness until its result is recorded. A live usage/headroom monitor and accepted private production runtime remain external acceptance gates. No cron handler is registered and no production budget is granted.

## Storage, restore verification and access

R2 was evaluated first using dated official sources in the capacity report. `R2ArchiveStorage` uses a private binding, conditional `If-None-Match:*` content-addressed objects, bounded body reads and timeouts. It makes no ETag-as-verification assumption or historical-version-retrieval promise. On timeout it cancels active bodies and cancels a late returned body. A timed-out put may complete as an unreferenced immutable object, which is safe to retry but still consumes budget. R2 production durability acceptance is deliberately false pending real storage/recovery acceptance. Source Worker config contains no R2 binding and no live availability was observed. Subscription/billing activation remains unauthorized.

A separate pinned official SDK Node R2 adapter supplies the private Node transport. It derives the expected HTTPS account endpoint, takes explicit in-memory credentials, uses conditional immutable puts, caps body/response/timeouts, disables redirects/automatic retries and validates collision bytes. `MirroredArchiveStorage` verifies both writes/readbacks and can recover from either local copy. Worker binding semantics and actual signed local SDK HTTP requests are tested. Both adapters still report `productionDurabilityAccepted:false`; another bucket is not automatically an independent administrative failure domain.

Synthetic memory/directory adapters only support local tests. Private plaintext SQLite scratch uses restrictive permissions and an owner marker containing UID, PID, boot identity and start ticks. The bounded startup sweeper removes only sufficiently old marked directories whose owning process is absent; it preserves live/recent/unmarked/symlink/unknown-process cases. This is implemented crash hygiene, not secure erasure or encrypted-volume acceptance. Production encrypted scratch and custodians remain unaccepted.

Independent verification re-downloads immutable bytes through `readArchiveManifest`/`readArchiveRecords`, checks canonical UTF-8/schema/limits/tenant/year/order/path/hash/HMAC/GCM, reconstructs into an isolated temporary sink, and compares trusted checkpoint controls/identities. Evidence binds verifier version, exact manifest hash, tenant/year/run/checkpoint/key and verification time. Upload response alone never advances to verified. Tests reject mixed financial years/tenants, invalid UTF-8, traversal, missing/reordered chunks, truncation, wrong key/tag and mismatched controls. No compression is accepted, removing decompression-bomb ambiguity. Verification creates no real users, financial postings or notifications.

Manager `listArchives`/`readArchiveRecord`/`readArchiveStatement` authorize before and after the bounded read. Catalog pointers must be verified/published and match tenant/year/checkpoint. Four chunks/request by default; explicit continuation is required. Employee calls are denied server-side. No public bucket or signed URL is used. Flutter offers stable-ID read-only invoice/entry viewing and party statements with Arabic PDF/CSV; cached UI clears on authority/scope changes. Statement fragments pin the exact manifest hash, cap responses at 1 MiB/2,048 rows, and reconcile role-specific signed openings, period effects and closings. Historical references never become period postings; reversal effects require the matching immutable original. Cross-year fixtures carry a 20,000 opening into a 15,000 closing without duplicate opening effects. Indexed cross-year discovery remains absent: each selected year uses a bounded scan. Ordinary viewing never calls active ledger import.

## Active snapshot recovery and conditional feed pruning

`active_snapshot` version 1 is a separate retained full-data projection for sync protocol 2, not an annual archive or a financial opening posting. Private Node preparation uses SQLite and injected writers/catalog/storage. Its preparation pages are canonical **plaintext** financial data; the injection does not establish production encryption, durable retention, independent copies or key recovery. No production snapshot provider is configured. Bounds are 64 KiB record arrays/page, 24,000 bytes/record, 4,096 pages, 500,000 records and 256 MiB total. A header binds tenant, UID, role, membership epoch, checkpoint, history floor, counts and descriptor digest. Employee output contains only exact sanitized parties and that UID's submissions; manager facts are not sent for client-side filtering.

The gateway derives scope and the minimum history floor from authenticated server state, checks authority before/after I/O and rejects stale snapshot checkpoints. A fresh epoch binds a new immutable snapshot ID; matching scoped content can reuse independently revalidated staged pages. Additive schema 4 stores headers/pages separately from the active ledger. Installation validates complete content and immutable collisions, then merges accepted facts and publishes cursor C/history floor in one local SQLite transaction. Unsent IDs/payloads, attempts/retry state, drafts, conflicts and provisional facts remain recoverable; only normal server receipts acknowledge an outbox operation. The controller negotiates v2 only after bootstrap advertises it, fetches at most 16 missing pages per recovery attempt, and resumes staged work. V1 below the server minimum requires upgrade; any stale cursor below the floor requires resync.

The previous combined 20,000-record/16 MiB in-memory installer has been replaced. SQLite now owns sort, uniqueness and dependency lookup; Dart retains one page and at most 16 records during merge. Validated records enter the temporary SQL table in one native batch per 64 KiB page. Independent entries then use indexed bulk identity/party/outbox reads and at most 32 native write/audit operations per 16 entries; every new row still passes the full financial validator. Linked returns, reversals, payroll and shipment dependencies flush preceding writes and retain sequential indexed validation. Existing queued operations retain their receipt state and correction provenance remains immutable. [27 focused/overlapping regressions](../verification/continuation-2026-11-02/final-review/snapshot-bounded-apply.json) cover collisions, pending wire/retry/draft preservation, complex dependencies and revocation rollback. Incoming bounds remain 500,000 records/256 MiB/4,096 pages; the combined guard remains 1,000,000 records/512 MiB. This conservative sum may double-count overlap and refuses before active mutation. The numeric ceilings are refusal limits, not certified capacity.

Global staged record-array bytes are capped at 256 MiB. At most four uninstalled transfers and four installed proofs remain; eligible abandoned transfers can be reclaimed, but the current transfer, newer checkpoint/floor or future membership epoch are protected. Installed pages are reclaimed transactionally, while pending work and facts remain intact. An exact already-installed proof can bind a fresh membership epoch without another ledger download. [Current-source Android SQLCipher evidence](../verification/continuation-2026-11-02/native-durable/annual-nov6batch-final-summary.json) now passes 73,000→80,300 accepted entries plus one pending, real SIGKILL/fresh rollback/resume, reboot, complete controller/domain reports and RTL home/statement rendering. Install times were 459,395/447,914 ms; full-process DEBUG peak was 765,775,872 bytes on a 2,560 MiB x86_64 emulator. This proves the recorded scenario, not 1 GiB phones, physical ARM, release-memory or 16 KiB page runtime capacity.

`feed-pruner.mjs` prepares a private metadata-only plan for the exact contiguous raw manager-feed range used by the sealed manager snapshot. The plan binds ordered document-body hashes and provider update times to snapshot/run/checkpoint identity; strict reread verification produces a process-local branded plan. Each step checks every candidate before queuing any delete, then atomically updates history floor C, minimum sync protocol 2, the durable delete cursor and at most 20 manager `changes` deletes. New writes after C and all original entries, directories, submissions, reviews, receipts, locks, late/conflict/audit evidence and `employeeChanges` remain online.

Every step rechecks tenant deletion/enablement, Cairo year eligibility, current fencing lease, exact archive/snapshot/plan evidence, grace expiry, dependencies, client install/protocol acceptance, recovery/key acceptance and shared budget. Provider versions or bodies changed since plan capture, missing rows, regressed floors and inconsistent progress fail closed. Bounded Firestore retry costs are reserved conservatively. Synthetic rollback/restart/racing-runner tests pass; production adapter/storage acceptance remains unestablished. There is no cleanup HTTP route, scheduled cleanup runner or production invocation.

## Tamper evidence and disaster recovery

Hashes plus manifest MAC detect byte modifications under uncompromised key custody. An administrator able to replace metadata, objects and key authority can rewrite this evidence; a chain in the same mutable database cannot prevent it. An external signed evidence anchor and an independently controlled recovery copy/key escrow are prerequisites for the declared disaster-recovery model. Another mutable object under identical credentials is insufficient. Those arrangements are unavailable/unverified here; cleanup stays disabled.

An annual package is a financial view, not a complete system backup. Replacement recovery has three distinct cases:

| Source of an operation | Actual recovery limit |
|---|---|
| Accepted by the server | A freshly authenticated replacement can recover retained accepted history through feed/snapshot; production account/device transfer still requires the authorized operator mechanism |
| Pending and included in a durable portable backup | Encrypted import restores the same stable ID/payload/retry evidence, dependencies, drafts and conflicts; ordinary receipt handling determines acceptance and deduplication |
| Unsynchronized and stored only on the lost device | **Unrecoverable here.** Neither server replay nor an older backup can supply bytes never copied elsewhere |

`RecoveryBackup` uses AES-256-GCM and PBKDF2-HMAC-SHA256 (210,000 iterations), fresh salt/nonce, a minimum 12-character passphrase, 16 MiB plaintext and 23 MiB encoded-envelope ceilings. Primary pending backups cap each queue/draft/conflict collection at 1,000 items and check dependency/byte budgets before accumulation. A manager can explicitly choose a bounded full financial copy. Import does not transfer Auth credentials, licenses, device private keys, entitlement, cursors or server authority. Legacy plaintext financial JSON remains a compatibility path, not an encrypted recovery claim. The two-business R3 native replacement drill passed on its recorded earlier DEBUG artifact and explicitly proved lost-only absence; final-source follow-up is separate.

`tenant-recovery-quarantine.mjs` captures the root and all 25 supported child collections into an encrypted synthetic image. Unknown/nested/orphan or unsupported data fails closed. Restore is create-only in `tenantRecoveryQuarantine/<image>/tenants/<tenant>`, commits each bounded page with a durable journal, resumes after interruption and verifies the exact logical inventory. The restored root is disabled and cannot activate users or devices. It retains receipt/counter/lock/member/device/archive metadata, but does not preserve provider update times or archive/snapshot object contents.

A separate read-only `firestore-recovery-source.mjs` captures supported tenant documents and inventories at one explicit provider `readTime`, preserving source create/update timestamps. It refuses automatic credentials, redirects, expiry, changed scope, unsupported field types, unknown/nested/orphan collections and bounded response/record/duration violations. The encrypted `firestore-recovery-image.mjs` reader authenticates pages and re-derives UID/key/object dependencies. [19 capture/image/plan tests](../verification/continuation-2026-11-02/final-review/recovery-capture-final.json) and [18 guarded quarantine tests](../verification/continuation-2026-11-02/final-review/recovery-quarantine-integration-final-v2.json) pass. The provider-shaped HTTP fixture is local; no real provider consistency acceptance is implied.

Actual archive/snapshot/catalog/closure bytes now have a separate bounded [object recovery consumer](recovery-objects-local.md). It authenticates the full image, rechecks artifact/inventory hashes, derives child identities from original-key-authenticated archive manifests and supported snapshot publications, refuses missing/cyclic/conflicting closure, performs immutable puts plus readback and resumes through a private durable SQLite journal. Objects cap at 1 MiB, separate metadata at 8 MiB, total at 512 MiB/40,000 objects; adapters bound reads before allocation and metadata receives a depth/token scan before parsing. [37 overlapping local tests](../verification/continuation-2026-11-02/final-review/recovery-objects-local.json) include real process SIGKILL, late puts, corrupted destinations, 10,240 snapshot records and metadata above 1 MiB. This is byte recovery into local quarantine, not financial activation, accepted provider storage or key custody.

The [authority recovery component](recovery-authority-local.md) separately authenticates Auth/operator packages and restores preserved UID/password-hash/salt bytes only as disabled accounts with operator history quarantined. [17 pure tests](../verification/continuation-2026-11-02/final-review/recovery-authority-pure-v2.json) and [12 real Auth/Firestore emulator tests](../verification/continuation-2026-11-02/final-review/recovery-authority-integration-v2.json) pass within those source receipts. The [financial-image binding](recovery-authority-binding-local.md) has [10 pure tests PASS](../verification/continuation-2026-11-02/final-review/recovery-integration-independent-review-binding-pure-nov7.json); actual combined coordinator integration remains pending. These component results are not whole-system disaster recovery acceptance. Actual provider qualification, independent storage/key custody, fresh enrollment and a separately reviewed activation procedure remain required; production activation is unimplemented and all acceptance/activation flags remain false.
