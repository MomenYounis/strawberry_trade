## Severity and evidence vocabulary

- **P0:** active/credible broad unauthorized financial access, irreversible corruption, or unrecoverable deletion. Stop the affected release/operation.
- **P1:** reproducible financial-integrity, authorization, recovery, or material availability defect. Must repair or disable the affected feature before release.
- **P2:** bounded correctness, defense-in-depth, availability/capacity, or operator-safety defect requiring a tracked remedy.
- **P3:** usability/documentation/maintenance issue with no demonstrated critical effect.

**Confirmed** means source and a reproduction support the defect. **Risk** means a relevant condition was identified but an exploit/business failure was not reproduced. **Untested** is not PASS. Local/emulator PASS does not establish production configuration or device acceptance.

## Architecture actually observed in source

The Android client uses Firebase Auth, device-held enrollment keys, SQLCipher/SQLite storage, and a durable local outbox. Trusted gateway functions apply immutable accounting events. The Cloudflare Worker forwards to a single named `TradingGateway` Durable Object (`gateway-v1`); its class is configured as SQLite-backed, but **the inspected gateway does not use Durable Object SQL as the authoritative ledger**. `worker/runtime.mjs` creates the Firebase Admin Firestore client. Records live under logical paths `tenants/{tenantId}/...` in a shared configured Firestore project/database. No source provisioner creates a separate project or database for each business. Five tenants do not receive five free project quotas.

`backend/firestore.rules` denies all client reads/writes. Those rules do not authorize Admin SDK operations: `gateway.mjs` independently validates Auth identity, verified email, revocation time, membership, device ownership, session, role, entitlement, and tenant namespace. Source configuration and older committed deployment reports are not independent live observations. No deployment was independently checked in this review.

| Historical read | Manager history UI/API | `listArchives`/`readArchiveRecord`: manager authority before and after storage reads; injected private viewer only | Read-only validated archive reader; never invokes sync/import/posting. Unconfigured adapter fails closed |

Date-only `entry.date` is the business effective/posting date. New feed records have authoritative `acceptedAtMs`, `sequence`, and `closeVersion`; legacy records are not retroactively assigned invented acceptance times. Late staging records server `receivedAtMs`; corrections keep `originalBusinessDate` separate. A client creation timestamp is not currently part of the operation contract and must not be confused with server acceptance.

## Dependency relevance and residual risks

Baseline `npm ci` in the original checkout failed `EROFS` because it is read-only and its pre-existing node_modules link is not usable here; original `npm test` was 39 PASS / 2 dependency-load failures. A disposable exact-HEAD source baseline using installed pinned dependencies passed **43/43**. This distinguishes environment failures from regressions.

The writable checkout uses Node 22.22.2 (repository runtime target), npm 10.9.7, Java 25.0.4. Pinned Firebase client/rules-testing dev dependencies declare Node >=24.12.0 and npm emitted `EBADENGINE`; tests currently run, but this unsupported dev-tool engine combination requires a separately validated CI Node toolchain. No pinned versions were silently changed to suppress warnings.

Initial `npm audit --omit=dev` found 1 high and 6 moderate graph findings. The reproduced body-parser high finding was repaired with a narrowly scoped lock change. Moderate findings involve `glob`/`minimatch` reached transitively through optional Google SDK support libraries (`gaxios`, `gcp-metadata`, `google-gax`, `rimraf`); the inspected gateway does not accept attacker-controlled filesystem/glob patterns or invoke those cleanup utilities in request handlers. This is a source-based reachability assessment, not proof the dependency graph is harmless. Broad major replacements (glob 14 / minimatch 11) were not forced into unrelated SDK dependencies. Maintainer review/compatible upstream fixes remain tracked: [glob cancellation advisory](https://github.com/isaacs/node-glob/security/advisories/GHSA-3g3m-2fjr-6pw4), [minimatch amplification advisory](https://github.com/isaacs/minimatch/security/advisories/GHSA-g3hv-75wg-m249), checked 2026-11-01.

The Worker dependency audit separately reported 8 moderate / 1 high findings, including `undici@7.29.1` only in the Wrangler/Miniflare development graph; see `worker-dependency-audit.json`. This is not an APK or Worker runtime dependency. Keep local dev servers bound to loopback and apply compatible vendor patches after verification. No automatic major update was made.

Additional **risks / unverified assumptions**, not claimed reproduced defects:

- Mutation rate control is tenant-wide (600 operations/minute); reads/bootstrap can still consume quotas. Historical read limits bound each page/chunk, not aggregate hostile traffic. Provider/identity rate limits and live budget headroom need validation.
- Auth revocation and Firestore writes cannot form one cross-service transaction. Financial writes recheck Firestore authority/session; transport verifies revoked Auth tokens at ingress. Exact revocation races across providers need a declared operational model.
- Review/return/reversal/correction dependencies remain online. Unlinked returns are an existing accepted product behavior, not a guarantee of invoice-linked limits for every return; business policy must explicitly accept this before claiming universal invoice-return enforcement.
- New parties' signed initial balances have no business date; salary terms use effective month and payroll payments may settle prior obligations. Sequence-frozen closing controls avoid mutating old checkpoints, but live cumulative reporting is not a full dated accrual-ledger model.
- A new phone can replay the full retained feed, but no complete compact snapshot installer or post-pruning rollback is proven. Therefore cleanup remains disabled regardless of archive upload success.
- Manifest confidentiality boundary: the manifest is HMAC-authenticated plaintext and contains private account IDs and financial controls/balances. AES-GCM chunk encryption does not conceal manifest controls. Restrict manifest/run-evidence access as financial data; storage-provider confidentiality of controls would require a separately encrypted manifest envelope, which is not implemented.
- No independent recovery copy/keys or live archive access was tested. Archive viewing tests are synthetic and cannot substitute for approved durable-storage acceptance.
